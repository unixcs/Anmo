## 三、缺陷清单

### BLOCKER

**B1 现金/微信收款并发双写：一个预约可产生多笔 VALID payment，违反 D1**
- 现象：同一"服务中"预约并发 3 笔 `SettleByPay` 全部返回成功，落库 3 笔 VALID 收款（真实 provider 并发、round=0 即命中，HTTP 层同样复现）；两条事务按代码语句序列交错亦确定性复现 2 笔 VALID。与核销路径（CARD payment）并发同样无互斥。
- 复现用例：`TestREVEAL_A5_ConcurrentCashDoubleInsert`、`TestREVEAL_H4_ConcurrentCashPayments`
- 根因：
  - `server/internal/modules/transaction/settle.go:180-187` —— `SettleByPay` 用非锁定一致性读 `SELECT COUNT(*) FROM payment WHERE appointment_id=? AND status='VALID'` 做 check-then-insert，REPEATABLE READ 下两个事务都读到 0；
  - `settle.go:188` 对预约行的 `SELECT ... FOR UPDATE`（GetTx）发生在 COUNT **之后**，不保护检查；
  - `server/migrations/006_transaction.sql:19` payment 表只有普通索引 `idx_payment_appointment`，无 `(appointment_id, status='VALID')` 唯一约束（对比 redemption 的 `uk_redemption_active_lock`）。
- 影响：收款双计/多计，`/admin/payments?status=VALID` 营收统计虚增，直接违反冻结决策 D1"一预约最多一笔 VALID payment"。

### WARNING

**W1 撤销后重放旧幂等键：200 成功响应 + payment 错配**
- 现象：核销→撤销→重放原 key 返回 HTTP 200 `{redemption: REVERSED, payment: null}`；若撤销后又重新核销（key2），重放 key1 返回的却是 **key2 那笔 VALID payment**（两次结算数据错配）。
- 复现：`TestREVEAL_A3_...`、`TestREVEAL_H5_...`
- 根因：`settle.go:88-96` 命中 idempotency 唯一索引即原样返回；`settle.go:249-257` `paymentForRedemption` 按 `appointment_id + method='CARD' + status='VALID'` 反查 payment，撤销后返回 nil、重新核销后错误匹配到第二笔。无资金损失、无双扣（红线未破），但响应语义含糊且数据错配。

**W2 SettleByPay 完全忽略 idempotency_key**
- 现象：同 key 重放返回 409 `PAY_EXISTS`，而非幂等回放原结果；请求体的 idempotency_key 被静默丢弃（payment 表无该列）。
- 复现：`TestREVEAL_A4_...`（证据日志）
- 根因：`settle.go:165-201` 接收并校验非空后从未使用；违反 AGENTS.md"幂等键 + UNIQUE 防重复提交"的契约。

**W3 跨会员卡核销被接受**
- 现象：A 的预约可用 B 的卡核销：HTTP 200，B 余额 10→9，redemption.member_id 记为 A（预约人），资金记到了错误的会员头上。
- 复现：`TestREVEAL_A14_...`、`TestREVEAL_H6_...`
- 根因：`settle.go:108-115` 与 `card/redeem.go:31-57`（ValidateForRedeem）的校验链（状态/有效期/余额/卡服务规则）不含 `card.MemberID == apt.MemberID`。

**W4 卡作废后撤销核销被整体拒绝，误核销的 CARD payment 永久 VALID**
- 现象：核销 → 作废卡 → 撤销 → `CARD_CANCELLED` 整体回滚；该笔 payment 永远停留 VALID，无法修正、无法计入 D1 的 VOIDED 口径。
- 复现：`TestREVEAL_A15_...`
- 根因：`card/redeem.go:93-95` ApplyReversal 拒绝 CANCELLED 卡；D12（作废不改次数）未定义与撤销事务的交叉场景，`settle.go:236` 又把恢复次数放进同一事务。

**W5 撤销把过期（EXPIRED）卡"复活"为 ACTIVE**
- 现象：卡过期并被 sweep 后撤销核销 → 卡状态被置回 ACTIVE，valid_until 仍为过去（显示可用，实际不可核销）。
- 复现：`TestREVEAL_A16_...`
- 根因：`card/redeem.go:98-101` 无条件 `SET status='ACTIVE'`（仅排除 CANCELLED）。

**W6 撤销原因超长时，插入失败被误报为"该核销已撤销"**
- 现象：reason > 500 字符（redemption_reversal.reason VARCHAR(500)）→ 插入报 1406 → 被映射为 `RDM_ALREADY_REVERSED`，操作者会误以为撤销已生效（实际整体回滚）。
- 复现：`TestREVEAL_A17_...`
- 根因：`settle.go:226-230` 把 `INSERT INTO redemption_reversal` 的一切错误一律映射为 `Conflict("RDM_ALREADY_REVERSED")`。

**W7 良性并发以 500 与死锁暴露（无数据损坏）**
- 现象：① 撤销与"撤销后重新核销"并发：6 轮中 5 轮 MySQL `Error 1213 Deadlock`（客户端收到 500 `CARD_LOCK: internal error`）；② 同一预约并发异 key 核销：撞 `uk_redemption_active_lock` 以 500 `RDM_INSERT` 暴露而非 409。
- 复现：`TestGUARD_A8_...`（日志）、`TestGUARD_A6_...`（日志）
- 根因：锁序相反 —— 撤销 `settle.go:215`（redemption FOR UPDATE）→ `card/redeem.go:89`（卡行），核销 `settle.go:108`（卡行）→ `settle.go:127-134`（INSERT 撞 active_lock 记录锁），构成 ABBA；且 1062/1213 未映射为业务冲突码。

**W8 CONFIRMED 预约可被直接核销并跳过 IN_SERVICE（偏离冻结状态机）**
- 现象：CONFIRMED 预约直接 `SettleByCard` 成功，预约状态 CONFIRMED → COMPLETED。
- 复现：`TestREVEAL_A18_...`
- 根因：`appointment/queries.go:49-54` MarkCompleted 显式允许 `IN_SERVICE` 或 `CONFIRMED` 结算；冻结状态机（AGENTS.md）只有 `IN_SERVICE → COMPLETED`。若是有意支持需回写口径文档，否则收紧。

### 已验证的健壮性（正面确认）

1. **卡余额不变量**：16 协程混战、同卡双核销竞态、6 协程并发撤销、撤销×重核销竞态下，`remaining_count >= 0` 恒成立，card_transaction 链与 remaining_count 账实完全吻合，无丢失更新（A1/A6/A7/A8 + 既有 `TestConcurrentRedeemOneBalance`）；DB CHECK `ck_member_card_remaining` 兜底。
2. **作废卡**：作废后核销/调整/重复作废全部拒绝，无任何次数流水（A1/A2）。
3. **核销幂等**：同 key 重放返回原记录不重复扣；同预约异 key 并发核销被 `uk_redemption_active_lock` 恰好拦到 1 个赢家；并发撤销恰好 1 次生效、次数只恢复一次（A6/A7 + 既有 e2e Case 6）。
4. **预约日历锁（D5）**：GET_LOCK 专用连接 + 事务提交后才释放的顺序正确；30 协程 DB 风暴、24 并发 HTTP 风暴（均超连接池 20）无死锁、无 5xx、恰好 1 个赢家；"锁等待期间目标时段被第三方占用"后改期仍被正确拦截（A9/A10/A13/H7）。
5. **冲突口径**：NO_SHOW / CANCELLED 不参与冲突判定，可重新预约（A11）。
6. **营业时间（D15）**：跨午夜 23:30、超打烊 20:30+60min 被拒；"结束=打烊"边界允许；30 分钟时间槽对齐校验生效；改期路径同样受约束（A12）。
7. **认证边界**：46 个 /admin 端点对顾客 token 一律 403、对无 token/垃圾 token 一律 401；ADMIN token 访问顾客端被拒；JWT 伪造（错 secret、过期、alg=none、RS256 混淆、篡改、空 act）全部失败（H1/H2）。恢复中间件 `Recover` 存在（middleware.go:100）。
8. **跨顾客隔离**：读/改期/取消他人预约 403；列表与卡列表无横向泄漏；预约归属强制取自 token（H3）。
9. **SQL 注入**：全部查询参数化（抽查 transaction/appointment/card 的 queries 与列表过滤），无字符串拼接用户输入进 SQL。

## 四、修复建议

- **B1**：payment 表加生成列 `valid_lock CHAR(26) AS (CASE WHEN status='VALID' THEN appointment_id END) STORED` + `UNIQUE(valid_lock)`（照抄 redemption.active_lock 模式），并将 `SettleByPay` 的 COUNT 检查改为先对预约行 `SELECT ... FOR UPDATE` 再检查。
- **W1**：replay 命中时按 redemption id 关联 payment（redemption 记录 payment_id，或撤销后显式返回 `payment: null` 语义并在响应中带上 `reversed: true` 标志），禁止按 appointment+method+VALID 反查。
